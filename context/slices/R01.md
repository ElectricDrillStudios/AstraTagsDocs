## Method

Work in two passes per page, in line with the style guide.

1. **Diagnose.** Reread the page paragraph by paragraph with the reader test. Mark each paragraph keep, reword, move, or cut. Typical failures to look for:
   - openings that state a mechanism before saying what the page helps the reader do (for example the first paragraph of the package configuration guide, which introduces lookups, indices, and ancestor masks before the reader has done anything; or an opening whose key sentence is a negation)
   - a term used before it is defined on the page or linked to its definition
   - a section that opens with a table or a rule without a sentence saying why it matters
   - runs of consecutive sentences with the same subject-verb shape
   - caveats written as "does not / never / without" where a positive statement and a callout would do
   - explanations that duplicate the introduction instead of linking to it
2. **Rewrite.** Change wording, order, and connective prose. Open each guide with a short, natural overview of what the reader will do and learn, then the running example. Keep numbered procedures, settings tables, code, callouts, and `IMAGE MISSING` comments; add a sentence of context before a table or procedure when it lacks one. Put a mechanism on the page that owns it, with the reason it matters to the reader's next action.

Rewriting means improving flow, not adding content. Do not introduce new claims, features, or examples that were not already on the page or verified in an earlier slice.

## Preservation rules

- Keep every programmatic identifier, menu path, Inspector label, file path, default value, number, code block, and link target unless it is explicitly accounted for in the report
- Keep headings and anchors that other pages link to. If a heading must change, update every inbound link in the same session
- Keep verified caveats, including those that document source findings F05 through F08 in the state; reword them, do not drop them or soften what they say
- Do not change behavior descriptions to read better. When a sentence cannot be made clear without changing its meaning, check the source, and if the claim is wrong correct it and report the correction separately from the editorial changes
- Do not edit generated output or the shared guidelines

## Acceptance criteria

- Every in-scope page passes the five-point reader test; the report lists, per page, how many paragraphs were reworded, moved, or cut, and quotes at least one before/after pair for the most significant change
- A token preservation check was run on each page and its result is in the report. Compare the file at the previous commit with the new file for: inline-code spans, bold labels, numbers, link targets, headings, and `IMAGE MISSING` comments. Keep the throwaway script in the scratchpad directory, not in the repository. Every removed or changed token is listed with its reason (moved to which page, replaced by which wording, or deliberately removed as a mechanism with no reader task)
- Read in the order Introduction, Installation Instructions, Creating and Organizing Tags, Package Configuration and the Registry, Tag Sets and Matching, Integrating Custom Tagged Assets, no term is used before it is defined or linked, either within a page or across the sequence
- Mechanisms that were removed from the introduction (registry lookup structures, editor versus runtime registry selection, fallback matching, indices and masks) remain explained, accurately, in the package configuration guide
- DocFX builds with 0 errors and only the five registered missing-image warnings; all local Markdown and HTML links, anchors, and resources pass; navigation and page URLs are unchanged
- No page grows meaningfully because of added content; length changes come from connective prose replacing terse fragments, and any large growth is explained
